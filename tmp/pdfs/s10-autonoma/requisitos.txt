1. De dónde partimos 
En la actividad práctica (Reto 01) PharmaBackend aprendió a preguntar quién llama y qué puede hacer: las 
contraseñas se guardan con BCrypt, el login entrega un JWT y cada endpoint exige su permiso. Pero una 
seguridad que no se prueba es solo una suposición. ¿Qué pasa si alguien altera el token, si lo envía sin el prefijo 
Bearer, si el administrador desactiva a un vendedor que ya tenía sesión o si un almacenero intenta registrar 
una venta? 
Además, la administradora de la botica pide tres cosas: que cada trabajador pueda cambiar su propia 
contraseña, que ella pueda cambiar los roles de un usuario cuando cambia de puesto y que pueda desactivar 
a quien deja de trabajar, sin borrar su historial. 
 
Reto 02 
Prueba sistemáticamente la autenticación, los tokens y los permisos de PharmaBackend con una matriz de 
casos medidos, e implementa el cambio de contraseña del usuario autenticado, la asignación de roles y la 
activación o desactivación de usuarios por el administrador.

Parte B. Contraseña, roles y estado de los usuarios (7 puntos) 
B1. Cambio de contraseña del usuario autenticado (3 puntos). Cualquier usuario autenticado puede cambiar 
su propia contraseña: 
 
PUT /api/v1/auth/password          (requiere token, cualquier rol) 
{ 
  "passwordActual": "Vendedor2026*", 
  "passwordNueva":  "NuevaClave2026" 
} 
→ 204 No Content 
 
▪ DTO CambioPasswordRequestDTO con las mismas reglas de contraseña de UsuarioRequestDTO para 
passwordNueva (8 a 72 caracteres, al menos una letra y un número). 
▪ El usuario se obtiene del token (Authentication), nunca de un id enviado en el cuerpo. 
▪ Si passwordActual no coincide con el hash ( passwordEncoder.matches) → 409 «La contraseña 
actual no es correcta». 
▪ Si la nueva es igual a la actual → 409 «La nueva contraseña debe ser distinta de la actual». 
▪ Se guarda passwordEncoder.encode(nueva) y se registra un log INFO con el usuario, sin contraseñas.

B2. Asignar roles a un usuario (2 puntos). Solo el ADMIN. Reemplaza el conjunto de roles del usuario (relación 
muchos a muchos): 
 
PUT /api/v1/usuarios/{id}/roles 
{ "rolIds": [2, 3] } 
→ 200 con UsuarioResponseDTO (roles y permisos actualizados) 
 
▪ DTO AsignarRolesRequestDTO con @NotEmpty Set<@NotNull Long> rolIds  → 400 si viene 
vacío. 
▪ Usuario inexistente o algún rol inexistente → 404. Un ADMIN no puede quitarse a sí mismo el rol ADMIN 
→ 409. 
▪ Basta con usuario.setRoles(new HashSet<>(roles)): JPA actualiza las filas de usuario_roles. 
▪ Comprueba que, con el mismo token, el usuario obtiene el nuevo permiso en su siguiente petición, y 
explica por qué en el informe (pista: revisa qué hace JwtAuthenticationFilter con el username). 
B3. Activar o desactivar usuarios (2 puntos). Solo el ADMIN (permiso USUARIOS_ADMINISTRAR): 
 
PATCH /api/v1/usuarios/{id}/estado 
{ "estado": false } 
→ 200 con UsuarioResponseDTO 
 
▪ Usuario inexistente → 404. Un ADMIN no puede desactivarse a sí mismo → 409. 
▪ Comprueba que el token que el usuario desactivado ya tenía deja de funcionar en su siguiente petición 
(401 «El usuario está deshabilitado») y que su login responde 401. 
▪ Agrega los casos B-01 a B-08 de las partes B1, B2 y B3 a tu matriz (no cuentan dentro de los 4 propios).

▪ C2. Fichas de hallazgos:  una por caso que falla, con descripción, severidad, evidencia, causa probable

▪ C3. Preguntas de análisis, respondidas en un párrafo cada una: 
1. ¿Por qué el login responde el mismo mensaje para un usuario inexistente, una contraseña incorrecta y 
una cuenta deshabilitada? ¿Qué información le daría a un atacante un mensaje distinto? 
2. Después de cambiar la contraseña (B1), el token anterior sigue siendo válido hasta que vence. ¿Por qué 
ocurre en una API sin estado? Propón una forma de invalidarlo. 
3. Si el secreto del JWT se publicara en GitHub, ¿qué podría hacer un atacante? ¿Qué harías de inmediato? 
4. ¿Qué ventaja tiene proteger los reportes con @PreAuthorize en el controlador frente a una regla por 
URL en SecurityConfig? ¿Y qué desventaja?

4. Dudas frecuentes 
Pregunta Respuesta 
¿Cómo obtengo el usuario autenticado en 
el controlador? 
Agrega un parámetro Authentication authentication al método 
y usa authentication.getName(), como en GET /auth/me. 
¿Qué excepción uso para «contraseña 
actual incorrecta»? 
ReglaNegocioException, que GlobalExceptionHandler ya 
convierte en 409. 
En T-03 cambié el secreto y ahora ningún 
login funciona. 
El login sí funciona: lo que falla son los tokens anteriores, que es justo 
lo que pruebas. Haz login otra vez y restaura el secreto al terminar. 
¿Cómo sé si un ADMIN intenta desactivarse 
a sí mismo? 
Compara el username del token (authentication.getName()) con 
el del usuario que se va a desactivar. 
En A-04 el login con mayúsculas funcionó. 
¿Está mal? 
No necesariamente: el repositorio busca sin distinguir mayúsculas. 
Decide si es la regla correcta y justifícalo en el informe. 
¿Cómo reemplazo los roles de un usuario? Busca los roles con rolRepository.findAllById(...), verifica 
que lleguen todos y asigna usuario.setRoles(new 
HashSet<>(roles)) dentro de un método @Transactional. 
¿Debo construir una pantalla en Angular? No. Esta actividad es solo de backend; el login en la SPA es el tema de la 
sesión 11. 
Cuando termines, la pregunta con la que empezó la sesión tendrá una respuesta completa. En el Reto 01 
protegiste PharmaBackend: contraseñas con BCrypt, un login que entrega un JWT firmado y permisos que cada 
rol trae consigo. En el Reto 02 demostraste, con  casos medidos, que un token alterado, ajeno o vencido no 
abre ninguna puerta, que cada rol solo llega a lo que le corresponde y que el administrador puede retirar el 
acceso a quien ya no debe tenerlo. Esa es la diferencia entre una API que funciona y una API en la que la botica 
puede confiar.
